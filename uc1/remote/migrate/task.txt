You are on a Nevia computer. Your task: migrate the MongoDB database {{MONGO_DB}} to a Nevia
Postgres database with mongo2pg, improving the generated SQL mapping (DDL and mappings) until all
the data loads, and prove it with a verification that passes. Each attempt runs on a new branch of
the database; the branch of an attempt that fails stays as it is, as the record of that failure.
The main database gets the migration last, once a branch has passed. The point of this lab is to
find the mongo2pg issues no one knows yet: the known ones are fixed first.

Steps:
1. Read context/CONTEXT.md and known-issues.md. Do not explore what CONTEXT.md already says. Check
   each known issue in this project as known-issues.md says, then fix all those that show in one
   pass, run `node unmapped.mjs` once for the fields no mapping covers, regenerate once (to-pg,
   export) and make the first attempt. Look for new issues only in what the attempts show.
2. Attempts, each on a new branch (nvpg branch): load the DDL and the data with mongo2pg import
   using the branch's config (or psql for the DDL if mongo2pg cannot), run known-fixes.sql on that
   branch, then the verification (step 3). An attempt fails when the load or the verification
   fails: stop writing to its branch, leave it as it is, fix the cause, and make the next attempt on
   a new branch. Never fix a failed branch in place. After you change a mapping, regenerate what
   depends on it (to-pg, export) rather than patching by hand twice.
   Always run mongo2pg with --log-level error (to-pg, export, import): its default output is long,
   and the error you need gets lost in it.
   Fix the DDL and mappings of the project only, e.g. CREATE DATABASE or OWNER TO postgres (no
   such role on Nevia), VARCHAR(n) sized from the values seen, NOT NULL on fields that are not always
   present, a type that does not fit every value (mixed types, dates, numbers too large), names
   that collide or are reserved, foreign keys the data does not satisfy, a child table that is
   better as columns of its parent or as JSONB, a field that no mapping covers.
   Every change you make to what mongo2pg generated is a mongo2pg issue, to improve the tool
   later: record each one, even a trivial one (a VARCHAR(n) too short, a function it calls that
   does not exist, a type it inferred wrong, a file it names wrongly), when you meet it. If no
   mapping can work around it, a SQL fix run after the import is allowed: add it to
   known-fixes.sql, and say so.
   {{WORK}}/mongo2pg-issues.json is the list of them, a JSON array, one object per issue (the same
   cause in several tables is one issue, with every place it hit):
     {"id": "<short-kebab-case name of the cause, e.g. varchar-sized-from-sample; a known issue
             keeps its id>",
      "known": <true for an issue of known-issues.md that still shows, false for a new one>,
      "kind": "bug | inference | postgres | feature",
      "command": "<infer | to-pg | export | import>",
      "places": ["<collection>.<field> or <table>", ...],
      "first_seen": "<known, analysis, or the branch, e.g. try1>",
      "observed": "<what mongo2pg did, with the error message if any>",
      "expected": "<what it should have done>",
      "workaround": "<what you changed: file, mapping, SQL>",
      "suggestion": "<how mongo2pg could do it right>"}
     kind: bug = wrong output; inference = a wrong guess from the data (type, mode, size);
     postgres = valid elsewhere, refused by PostgreSQL 18 or Nevia; feature = something missing.
   For a known issue, places and observed are what you saw in this run; the rest may be shorter
   than in known-issues.md.
   Every collection of the project must be migrated: they are the collections with documents (the
   empty ones are excluded in the config).
3. Verification: `node verify.mjs try<N>` on each branch that loads, `node verify.mjs main` on the
   main database. It prints the FAIL lines and a summary, and exits non-zero on any FAIL; every
   check goes to verify-<target>.txt, the results to verify-<target>.json. Read the .txt only for
   a FAIL the summary does not explain. It checks:
   - for each collection, countDocuments in MongoDB equals the rows of its table;
   - for each child table, its rows equal the number of elements (or sub-objects) mongo2pg maps
     to it, counted in MongoDB with an aggregation;
   - for each collection, up to 50 documents taken at random ($sample), every mapped field
     compared with its row(s): strings exactly, numbers, booleans, dates to the millisecond,
     a missing field as NULL, JSONB as the same JSON;
   - no VARCHAR(n) sized from the sample left in the mappings (they load today, and fail on the
     next longer value);
   - primary keys unique, no orphan row for any foreign key;
{{CHECKS}}
   A FAIL may come from verify.mjs itself (or checks.mjs): fix it there if so, and say so.
4. When a branch passes the whole verification, apply the same migration to the main database
   (nvpg config without a name gives its config): import, known-fixes.sql, then
   `node verify.mjs main`. It is empty at the start of the run.
   If it fails there, that is a failed attempt too: fix the cause and start again on a new branch.
5. Once verify.mjs passes on the main database, write mongo2pg-issues.json and REPORT.md, once
   each, from what you already know, and stop: no more checks, no other run of verify.mjs or
   unmapped.mjs, no rereading what you wrote. The figures of the report come from the verification
   (the script adds them).
