The migration in detail.

Configuration: in src/main/resources/application.properties, set database.kind from mongo to
postgres. The deploy layer reads that key at every deploy and then gives the application a
Postgres database instead of MongoDB: do not remove it. Read the new settings the way the code
already reads its configuration.

The application then receives, instead of MONGODB_URI and the tunnel variables (MONGO_TUNNEL_URL,
CHISEL_USER, CHISEL_PASSWORD), the two below. Point the keys of application.properties at them
(the database URI at ${DATABASE_URL}, and a key for the certificate that may be empty):
- DATABASE_URL: a libpq-style URI, postgres://user:password@host:port/database?sslmode=require,
  which JDBC cannot take as is. Convert it to jdbc:postgresql://host:port/database plus user and
  password properties (they are URL-encoded in the URI).
- PG_CA_FILE: the path of the server certificate, relative to the sources directory. When it is
  set, verify the server with sslmode=verify-full and sslrootcert; otherwise sslmode=require.

The data model:
- Every collection the application uses becomes normalized relational tables: a table for its
  documents, a child table for each nested list (and for each nested object when it is not better
  as columns of its parent), with primary keys, foreign keys, and ON DELETE CASCADE from a document
  to what belongs to it. Add the indexes the application's queries need.
- Create the schema at startup when it does not exist.
- Write a document and everything it holds in one transaction: a failed write leaves nothing half
  stored. Where the application replaces a document, or a list in it, as a whole, keep doing so.

The mongo2pg analysis is evidence for the schema, not the schema:
- Start from its tables (tables/, mapping_*.yaml) and check each column against the data: a field
  whose presence probability is below 1 is nullable, its types tell the column type.
- It saw a sample of the data only, so its limits are not rules: do not keep a VARCHAR(n) sized from
  the values seen, nor a NOT NULL that the application's own validation does not require. The rules
  of the code and the requirements below win over it, e.g. ON DELETE CASCADE, which it does not add.
- Handle every infer warning of its stats.yaml files: say in the pull request what it is about and
  what you did with it.
- Do not copy it into the repository: the search for mongo below does not cover it.

Requirements:
- Target: PostgreSQL 18, on Nevia as in the local development setup (image postgres:18). Use its
  SQL freely, nothing newer.
- pom.xml: replace the MongoDB driver with the Postgres JDBC driver, and bump the version. The
  versions to use, all on Maven Central (no need to look for others, e.g. in ~/.m2):
  org.postgresql:postgresql 42.7.14; for JSON, com.fasterxml.jackson.core:jackson-databind 2.22.4
  (and com.fasterxml.jackson.datatype:jackson-datatype-jsr310 2.22.4 if dates need it).
- Keep the HTTP API exactly as it is: same routes, same status codes, same JSON shapes (nested
  lists stay nested in JSON, whatever the tables), same validation and messages, same behaviour
  for a database that does not answer, same retry at startup if there is one. Dates keep their
  current JSON form. A user interface served by the application must work unchanged; adapt its
  text only where it names MongoDB.
- If the code reads or writes JSON with MongoDB's BSON classes (Document, JsonWriterSettings…),
  replace them with one small, well-known JSON library (for example Jackson), not a hand-written
  parser.
- Seed data: the MongoDB data of the repository is in local/mongo-init/*.js (mongosh scripts run
  against the application's database). Turn them into local/postgres-init/*.sql, the same data
  with the same ids, and delete local/mongo-init. The convention for these files, which the
  deploy layer follows too:
  - plain SQL run by psql in the order of their names (e.g. 01-schema.sql, 02-customers.sql),
    against the application's database, as the postgres image's /docker-entrypoint-initdb.d does;
  - the first creates the schema, exactly the one the application expects (the tables, keys and
    constraints of its own schema creation, if it has one: both must stay compatible, e.g.
    CREATE TABLE IF NOT EXISTS on both sides);
  - then the data, in INSERT statements, in an order the foreign keys accept;
  - they must run without error on an empty database, in a single transaction each.
  The deploy layer loads them into the new, empty Postgres of the sandbox before the application
  starts: the application there must show the same customers as before the migration.
- Local development: if the repository runs MongoDB locally (docker-compose.yml), replace it with
  Postgres: same service role, local/postgres-init mounted as its /docker-entrypoint-initdb.d. The
  application started against it must show the same content as before.
- Do not migrate the data that is in MongoDB on Nevia: on Nevia, the application starts over with
  the seed data of local/postgres-init only. Say so in the pull request.
- Tests: keep the tests in src/test passing and adapt them to the new code. Put the conversion of
  the libpq URI into a method that needs no database, and add unit tests for it: user and password
  decoded, port missing (5432), sslmode with and without a certificate. Keep the tests that need no
  database testing without one. The build runs them (mvn -q -B package): a failing test stops the
  pull request.
- Remove MongoDB from the whole repository: the Java code (no driver import, no leftover class,
  method, field or comment), pom.xml, application.properties, the local development files, the
  README and the text of the user interface. When you are done, search the repository for mongo,
  mongodb, chisel, tunnel and bson, outside target/: it must come back empty. Say in the pull
  request that you ran that search.
